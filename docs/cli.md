# The standalone binary

A single Go binary built on the **go-c8y v2** library, talking to the REST API
directly instead of shelling out to `c8y`. Same commands as
[the extension](extension.md) and the same behaviour — a differential test diffs
their output on every build — plus a `preflight` command of its own.

What it migrates, and the limits it enforces, is in
[the main README](../README.md). Why it exists is in
[docs/internals.md](internals.md#why-there-are-two-implementations).

It reads the same session files `go-c8y-cli` writes, including encrypted ones —
`C8Y_PASSPHRASE` is used exactly as `c8y` uses it. Unlike `c8y` it does not need
a session to be active first, and it refuses a `--session` glob that matches more
than one file rather than silently taking the first.

## Building and installing

From a release, which is the easiest way and needs no Go toolchain — pick the
archive for your platform from the
[releases page](https://github.com/Cumulocity-IoT/c8y-devicemigration/releases),
check it against `SHA256SUMS`, and put the binary on your `PATH`:

```sh
tar -xzf c8y-devicemigration-<version>-darwin-arm64.tar.gz
shasum -a 256 -c SHA256SUMS
```

`c8y-devicemigration --version` then says which build it is, which is worth
knowing before reporting anything about it.

Or from source:

```sh
make go-build   # -> bin/c8y-devicemigration
make install    # -> $(INSTALL_DIR), default ~/.local/bin
```

```sh
make go-build      # -> bin/c8y-devicemigration

# --session is optional: without it the active go-c8y-cli session is used
eval "$(c8y sessions set --sessionFilter source-tenant)"
./bin/c8y-devicemigration export --rootId 12345 --output-directory ./my-export

./bin/c8y-devicemigration preflight \
    --sourceSession 'source.eu-latest.cumulocity.com-me.json' \
    --targetSession 'target.eu-latest.cumulocity.com-me.json'

./bin/c8y-devicemigration export --rootId 12345 \
    --output-directory ./my-export \
    --session 'source.eu-latest.cumulocity.com-me.json'
```

It reads the same session files go-c8y-cli writes, including encrypted ones —
`C8Y_PASSPHRASE` is used exactly as `c8y` uses it. Unlike `c8y`, it does not need
a session to be active first, and it refuses a `--session` glob that matches more
than one file rather than silently taking the first.

**The port is complete**: `preflight`, `export`, `register`, `import`, `revert`
and `migrate`, covering the hierarchy, its external identities, its
relationships, the run marker fragment, device data — measurements, events,
alarms and event attachments — and `migrate`'s `--incremental` and `--resume`.

```sh
eval "$(c8y sessions set --sessionFilter source-tenant)"   # any session will do

./bin/c8y-devicemigration migrate --rootId 12345 \
    --sourceSession source.json --targetSession target.json \
    --dataTypes measurements,events,alarms --incremental --force
```

Because migrate calls the export and import in-process rather than shelling out,
there is no session plumbing between phases and no subprocess boundary to lose an
exit code across.

`--dataTypes all` is a shortcut for `measurements,events,alarms` in both
implementations. It cannot be combined with named types: `all,events` is refused
rather than guessed at, because either reading of it is plausible.

## Device credentials

A migration is a copy, and what does not come across is the devices' ability to
authenticate: their existing credentials belong to the source tenant. So a
migrated device sits in the target as a twin nothing is connected to until it is
given credentials of its own.

`--credentials` provisions them, and writes them to `--credentialsFile`:

```sh
./bin/c8y-devicemigration migrate --rootId 12345 \
    --sourceSession source.json --targetSession target.json \
    --credentials --credentialsFile ./credentials.csv
```

The file is comma separated, with `EXTERNAL_ID`, `TENANT`, `USERNAME` and
`PASSWORD`, and it is written `0600`. **It is the only copy.** The passwords are
generated in memory and are not recorded anywhere else, including in the target
tenant — issuing them again does not retrieve them, it replaces them.

Each password is 15 characters over letters, digits and punctuation, with at
least two of each class so a tenant's password strength policy cannot refuse it.
Five punctuation characters are excluded, and if a password ever has to be
regenerated by hand these are why: `,` and `"` because both files it travels
through are comma separated and the registration endpoint has been **measured**
not to honour RFC 4180 quoting — it splits on every comma and trims quotes rather
than unescaping them; `'` because the advice for pasting one into `curl` or
`mosquitto_pub` is to wrap it in single quotes; `\` because tools disagree about
whether it escapes; and a backtick because it is the one character that runs a
command if somebody uses double quotes instead.

### Why it registers before it imports

The devices are registered in the target **before** the hierarchy is imported,
and the order is not a preference. Bulk registration creates a managed object
owned by the device user it creates alongside it, and the import then fills that
object in with a `PUT`. Registering *after* an import cannot give a device
ownership of an object that already exists — the platform treats a known external
id as a password rotation and leaves the object alone — and a device that does
not own its own twin cannot write to it.

That is also why an import only ever updates an object carrying **its own run's
marker**: everything else is created, exactly as before. `--adoptRegistered`
without a matching `--runId` finds nothing to adopt.

### Ownership, and why an import may stamp it

A device authenticates with `ROLE_DEVICE`, and that role carries writes **only
together with ownership of the object**. So a migrated device that later gets
credentials by some route other than `--credentials` can read its own managed
object and cannot write it — measured on a live tenant as `403` on updating the
object and `403` on posting a measurement against it. The fleet looks migrated and
silently sends nothing.

`--stampDeviceOwner` prevents that, on `import` and on `migrate`:

```sh
./bin/c8y-devicemigration migrate --rootId 12345 \
    --sourceSession source.json --targetSession target.json \
    --stampDeviceOwner
```

It names each device as the owner of its own object — `device_<externalId>`,
derived from the same identity `register` would use. That works even though the
device user does not exist yet: Cumulocity accepts an owner it has no user for,
on create as well as on update, and lines the two up when that user is finally
created. So nothing has to revisit the object per device afterwards.

You do **not** need it with `--credentials`. There the objects are created by the
registration phase and are already owned by their device users, so the two flags
are refused together. Reach for it when the credentials arrive by another route —
devices registered by hand later, or a certificate fleet whose devices
auto-register into the target.

Skipped, as with registration: groups, devices with no external identity, and
devices carrying several identities with none of the preferred type. The count of
what was stamped is in the import's summary.

### As three steps

`export`, `register` and `import` compose, for anyone who stages a migration by
hand. The run id is what ties the last two together:

```sh
./bin/c8y-devicemigration export --rootId 12345 \
    --output-directory ./out --session source.json

./bin/c8y-devicemigration register --input-directory ./out \
    --runId 20260908T101112Z_ab12cd \
    --credentialsFile ./credentials.csv --session target.json

./bin/c8y-devicemigration import --input-directory ./out \
    --runId 20260908T101112Z_ab12cd --adoptRegistered --session target.json
```

`register --dry-run` reports which devices would be registered and which would
not, and creates nothing — worth running first, because the answer is often not
"all of them".

### Which devices get credentials, and which do not

A device is registered under its `c8y_Serial` external identity, because that is
what an agent presents when it reconnects. Failing that, a device with exactly
one identity of any type is registered under that one.

Skipped, each with its reason on stderr:

| | |
| --- | --- |
| a group, or anything that is not a device | there is no device user to create |
| a device with no external identity | a device user could never be matched back to it |
| a device with several identities and no `c8y_Serial` | which one should own the user is not guessed at — `--identityType` chooses for the whole run |
| a device whose name, type or external identity contains a **comma**, a **quote** or a line break | the bulk registration file has no escaping — measured, not assumed — so such a row would be read with its columns shifted, and the platform accepts that silently. The value is refused rather than altered |

A skipped device is migrated like any other. It simply arrives without
credentials, which is worth knowing before the fleet is expected to reconnect.

### Identities the target already has

Registering an external identity the target tenant already holds does not create
a device. The platform treats it as the device of that name already existing and
**sets a new password on it** — so a device that has nothing to do with the
migration stops working with the credential it has.

So `register` and `migrate --credentials` resolve every identity they are about
to register against the target first, and **refuse the whole run** if any of them
is already there. Nothing is generated and nothing is created; the message names
each device on both sides so the duplicate can be looked at. There is no flag to
proceed anyway — the two ways forward are to migrate without `--credentials`, or
to settle the duplicate identities between the tenants first.

`register --dry-run` runs the same check and exits non-zero on the same answer,
so it can be used to find out whether a migration can carry credentials before
anything is exported.

### Rotation, resuming, and reverting

Re-registering a device this tool itself registered **rotates** its password: the
new one works, the old one stops, and any file handed out earlier is dead. Two
consequences:

- `migrate --resume` does **not** re-register. The credentials from the first
  attempt are still the valid ones, and re-issuing would invalidate them for
  devices that were already working. It says so and carries on.
- Migrating the same hierarchy twice with `--credentials` is refused by the check
  above, because the first run's identities are now in the target.

`revert` removes the device users along with the objects, in the same call — the
platform's `withDeviceUser` — so an undone migration leaves no credentials
behind that still authenticate. It needs no user-management permission for that.

**Nothing is removed from the source tenant**, including the devices' ability to
authenticate there. A migrated device ends up holding two working identities in
two tenants, and that is deliberate — a migration that disabled the source would
have no way back — but "migrated" reads as "no longer in the source", and here it
is not. Deprovisioning the source is a separate, manual step. A certificate fleet
is the exception: moving its trust anchor removes the certificate from the source,
so that fleet really does leave.

### Getting the file onto the devices

That part is yours. A configuration push through the source tenant while the
devices are still connected to it, a field technician, or existing
device-management tooling. This tool does not deliver credentials to devices, and
sending them as an operation through the source tenant would write plaintext
passwords into that tenant's operation log.

For a fleet on **certificate** authentication there is nothing to provision here:
the credential is the chain, and the devices keep it. That is a different
mechanism, and it is the microservice's — see
[moving a trust anchor](microservice.md#moving-a-trust-anchor-for-a-certificate-fleet).

## Confirmations

Destructive commands ask in the shape `c8y` asks, so the keys mean what someone
used to `c8y` expects:

```
Confirm (job: 1)
Migrate 12345 from source.eu-latest.cumulocity.com (t11223344) to target.eu-latest.cumulocity.com (t55667788)
[y] Yes  [a] Yes to All  [n] No  [l] No to All
```

`y`, `yes`, `a` and `yestoall` proceed; anything else, including an empty line,
declines — a typo must never be read as consent. `--force` skips the question.
The dialog goes to **stderr**, as c8y's does, so redirecting stdout does not hide
it.

One question rather than c8y's per-request dialog: `revert` has already printed
its whole plan by then, and asking once about that is clearer than asking N
times.

## Shell completion

```sh
make install-completion
```

That does both halves, because completion needs both:

1. **The binary has to be on `PATH` under its own name.** The generated script is
   keyed to the bare command name and calls the binary back to compute
   completions, so a `./bin/c8y-devicemigration` that is not on `PATH` completes
   nothing — silently. `make install` puts it in `$(INSTALL_DIR)`, which defaults
   to `~/.local/bin`.
2. **The script has to be somewhere on the shell's completion path.**
   `$(ZSH_COMPLETION_DIR)` defaults to Homebrew's `share/zsh/site-functions`,
   which is already on zsh's `fpath`.

Then start a new shell. If completions do not appear, zsh is serving a cached
completion dump: `rm -f ~/.zcompdump*; exec zsh`.

Both directories are overridable:

```sh
make install-completion INSTALL_DIR=~/bin ZSH_COMPLETION_DIR=~/.zsh/completions
```

For a directory of your own, add it to `fpath` **before** `compinit` runs:

```sh
fpath=(~/.zsh/completions $fpath)
autoload -Uz compinit && compinit
```

macOS zsh already runs `compinit`, so there is usually nothing to add.

For other shells:

```sh
source <(c8y-devicemigration completion bash)     # bash
c8y-devicemigration completion fish | source      # fish
c8y-devicemigration completion powershell         # powershell
```

Command and flag names complete out of the box. Flag **values** complete for the
ones with a knowable set:

| Flag | Completes to |
| --- | --- |
| `--session`, `--sourceSession`, `--targetSession` | the session files in the session home, by name |
| `--dataTypes` | `measurements`, `events`, `alarms`, `all` — comma-aware, dropping what is already chosen, and offering `all` only on its own |
| `--childTypes` | `asset`, `device`, `addition`, the same way |

`--rootId` is deliberately **not** completed. Resolving device names means
querying the tenant, and completion runs on every tab press: a shell that pauses
for an authenticated round trip is worse than one that completes nothing. That is
the one place `c8y` goes further, and it can afford to because it already has a
session loaded.

Dates work as they do in the extension, including relative forms like `-30d`,
with one difference worth knowing: the bash version handed them to `c8y` to
parse, so this one parses them itself and **refuses** a form it does not
understand rather than guessing at a window.

`revert` prints its plan and asks once before deleting anything, where the bash
version leans on c8y's own per-request dialog; `--force` skips the question in
both. It establishes what actually happened by re-reading every object rather
than trusting the delete responses, so propagation from a parent group and a
declined confirmation are both reported correctly.
`docs/go-port/BEHAVIOUR-CONTRACT.md` records what the two implementations have to
agree on, down to the trailing newline.
