# Migrating device credentials

> **Status: Option A is built; B and C are still concepts.**
> Option A shipped and its behaviour has moved up into `docs/` — what is left
> here is the record of why it took the shape it did, plus Options B and C, which
> are still proposals. One assumption settled along the way changed Option C
> materially — **Cumulocity resolves the tenant from the hostname a device
> connected to before it looks at the certificate** — so Option C no longer moves
> a fleet on its own. Its remaining assumptions are still assumptions; the
> procedures that settle them are in
> [credentials-verification.md](credentials-verification.md), and they gate that
> build.

A migration copies a device hierarchy — the managed objects, their relationships,
their external identities and, on request, their measurements, events and alarms —
into a second tenant on the same platform. The source is left untouched: it is a
copy, not a move. What does not come across is the devices' ability to
authenticate: their existing credentials belong to the source tenant.

This was the concept for closing that gap. Option A closed it for
basic-authentication fleets and is now
[documented behaviour](../../README.md#device-credentials); a certificate fleet is
Option C, and still a proposal.

## Why credentials cannot simply be migrated

| | |
| --- | --- |
| **Device user** (basic auth) | The password is generated by the platform at registration and is never retrievable afterwards. The username is tenant-scoped, and the user belongs to the source tenant's user store. |
| **X.509 certificate** | The device's certificate chains to a CA the tenant trusts, and a trusted certificate's fingerprint can be enabled in only one tenant per platform instance. Trust decides whether a connection is *accepted*, not where it *lands*: the tenant is resolved from the hostname the device dialled ([settled](#settled)). |
| **Access token** | Issued against a tenant after authenticating with one of the above, so it inherits their problems rather than solving them. |

The requirement suggests two ways out — an endpoint through which devices migrate
themselves, and a bulk credential download. Both are below, along with a third
that costs the devices no new credential.

### One piece of existing machinery makes all three possible

External identities are already migrated
([internal/export/export.go:174](../../internal/export/export.go#L174),
[internal/importer/importer.go:347](../../internal/importer/importer.go#L347)), so a
migrated device carries the same external id in both tenants. And every object a
migration creates is stamped with that run's marker fragment. Those two facts are
how any of the options finds *the copy of this device, made by this migration*,
without a new mapping to keep.

## Option A — built

**Complete.** Every question it rested on is answered, the code is in, the tests
pass, and the behaviour has moved up into `docs/` — this section is a pointer and
a record, not a proposal:

| | |
| --- | --- |
| What it does, and how to use it | [README](../../README.md#device-credentials), [docs/cli.md](../cli.md#device-credentials) |
| The microservice's one-time download | [docs/microservice.md](../microservice.md#device-credentials) |
| The screen | [docs/ui.md](../ui.md#the-credentials-download) |

The shape it ended up with is worth stating once here, because the verification
pass changed it and the reasoning is what stops it being changed back: the
devices are registered in the target **before** the hierarchy is imported, and
the import updates the objects registration created rather than creating its own.
Bulk registration creates a managed object owned by the device user it makes
alongside it; registering after an import only rotates a password and leaves the
object alone, so the device would never own its own twin.

What it cost, against what the concept guessed:

| | |
| --- | --- |
| **Manifest** | One role, `ROLE_DEVICE_CONTROL_ADMIN`. The user-management role this section once expected is not needed: `withDeviceUser` on the object delete removes the device user with the device, in both implementations. |
| **Order** | A phase between export and import, in `migrate` and as a `register` command. `--resume` deliberately does not re-register, because that would rotate passwords already handed over. |
| **Importer** | A second creation path, gated on the run's own marker so it can only ever update objects this run registered. The `owner` strip that made it safe was already there. |
| **Secrets** | Nowhere but the credentials file and, for the microservice, one in-memory handover. Never the job record, which any owner-tenant administrator can read. |

See [Settled](#settled) for each finding and
[credentials-verification.md](credentials-verification.md) for how they were
established — including the two that were wrong first time.

## Option B — self-migration, the device asks for its own credentials

A device calls one endpoint on the microservice, authenticated with the
credentials it already has for the source tenant. It sends **no parameters**. The
service works out the rest:

1. The caller's credentials are proven against the platform.
2. The device it *owns* in that tenant is found — a device user owns its managed
   object.
3. That object's external identities are looked up in the target tenant, and the
   copy found there must carry the marker of a succeeded migration.
4. A device user is created for that copy, and the new tenant, username and
   password are returned once. Issuance is recorded on the target device object,
   without the secret.

**What stops a device asking for someone else's credentials.** The endpoint takes
no input, so there is nothing to tamper with. The chain runs from the
authenticated caller to the object it owns, to that object's identities, to the
migrated copy. Impersonating another device would mean attaching that device's
external identity to an object the attacker owns, which the platform refuses —
the identity is already taken.

**What it costs.** It is the first deliberate exception to a rule the service
applies everywhere else: only users of the tenant it is deployed on may call it
([internal/service/auth.go:36](../../internal/service/auth.go#L36)). That exception
needs its own authorizer, its own tests, rate limiting and an audit trail. And it
needs something outside our control — firmware that can call an endpoint and
switch credentials. Realistic where the customer owns the agent; not realistic for
closed firmware.

**Assessment.** The most elegant answer for fleets that can use it, and the
largest security surface in the proposal. Worth building when a fleet that can
actually call it exists — not before.

## Option C — move the trust anchor, and point the devices at it

For a certificate fleet the credential is the chain, and it never has to change:
the device keeps its private key and its certificate, and a migration only has to
make the target tenant trust that chain. Read the trusted CA certificates from the
source tenant, recreate them in the target with auto-registration enabled, and at
cutover disable them in the source. Auto-registration then binds each arriving
device to its migrated copy through the external identity that came with it —
[unconfirmed](#to-confirm-on-a-live-tenant-before-building), and the rest of the
option rests on it.

### Trust is not routing

An earlier draft of this option claimed the devices need do nothing at all, on the
belief that the platform sends a certificate-authenticated connection to whichever
tenant trusts its chain. That was wrong, and it was the load-bearing assumption:
**Cumulocity resolves the tenant from the hostname the device connected to, and
only then checks whether that tenant trusts the presented chain**
([settled](#settled)).

Moving the CA therefore changes whether the target *accepts* a device, not where
the device *arrives*. A device left pointing at the source hostname keeps
connecting to the source — and once the CA is disabled there it is refused, with
nowhere else to go. The option has two halves and neither works alone:

| | | |
| --- | --- | --- |
| **Authorization** | which tenant trusts this chain | server-side, per CA — this tool |
| **Addressing** | which hostname the device dials | device-side, per device — an agent on the device |

Device involvement is *no new credential* rather than *nothing at all*: no new
certificate, no new password, no re-enrollment — but something on the device has to
rewrite the configured URL and reconnect.

### The device-side half

For thin-edge.io fleets that agent already exists as a separate deliverable, the
`tedge-environment-migration` package: a timer-driven shell agent that asks a
steering endpoint whether this device should move and where, rewrites `c8y.url`
(unsetting `c8y.http` and `c8y.mqtt` so both derive from it), runs
`tedge reconnect`, and restores all three if the reconnect fails. It changes no
credential at all — it migrates on the certificate the device already holds —
which is exactly the device-side complement this option needs, and is why it is
useless for Options A and B.

What it adds beyond the URL change is **granularity**: its steering endpoint
answers per device with a revocable instruction, so a CA-wide trust change can be
rolled out to a few devices at a time and stopped. That is the one thing this
option otherwise cannot offer, and it is worth pairing them for that alone.

Two of its behaviours constrain the cutover ordering. Both come from reading it,
not from testing:

- Its pre-flight probe authenticates with Cumulocity's **generic bootstrap
  credentials**, not the device certificate, so a target where the CA is
  registered but still disabled passes the probe. Devices then rewrite their
  configuration, fail the real connection and roll back — a fleet-wide revert that
  reads as a fleet-wide failure. **Enable the CA in the target before any device is
  told to move.**
- Its rollback assumes the source still works. Once the CA is disabled in the
  source, a device that fails to reach the target cannot go back either and lands
  in the agent's "connected to neither tenant" state. **Disable the CA in the
  source last**, after the fleet has been confirmed in the target.

Neither of the agent's own pre-flight gates can verify this option's work: its
certificate check validates the *platform's server* certificate against the
device's trust store, which is the opposite direction from "does the target trust
me". A device-certificate handshake as a further pre-flight would close that gap
and is worth requesting of that package.

### The cutover window

Because a fingerprint cannot be enabled in two tenants at once, the ordering has a
real availability cost: whether the certificate can be pre-staged in the target
while disabled and then flipped — a window of seconds — or must be removed from
the source first. Platform behaviour to confirm, not to assume
([C2](credentials-verification.md#c2--can-the-same-certificate-exist-in-both-tenants)).

> **The unit is the CA, not the hierarchy.** Every device chained to that CA moves
> at once. A partial migration therefore cannot cut over safely unless the CA
> belongs exclusively to the hierarchy that was migrated. The tool should count the
> devices in the source that the run did *not* cover, and say so before offering a
> cutover — which assumes a device can be attributed to the CA that signed it, and
> that is itself unconfirmed
> ([C7](credentials-verification.md#c7--can-a-device-be-attributed-to-its-ca)).

### Deliberately not in the first cut

Fleets enrolled against Cumulocity's own per-tenant certificate authority cannot
have that CA moved at all; they need re-enrollment, which is a separate mechanism
and a later increment. Per-device certificates issued by a customer's own CA are
covered by moving that CA — provided the target does not demand proof of
possession of the CA's private key, which neither this service nor the source
tenant holds
([C4](credentials-verification.md#c4--does-the-target-demand-proof-of-possession)).

### Assessment

Still the least work *per device*, and a small amount of code on
the platform side — but it is no longer a server-only option, and its total cost
now includes an agent on every device. Where such an agent already exists it is
the cheapest option by a distance; where it does not, Option A is cheaper than
writing one.

## Scope boundaries worth stating

- **Devices behind a gateway or agent** that holds credentials on their behalf:
  the gateway is the device, as far as this is concerned.
- **Sending new credentials as an operation through the source tenant** works and
  is tempting, but it writes plaintext credentials into the source tenant's
  operation log. It belongs in an operator's runbook if they accept that; it
  should not be something the tool does for them.
- **Nothing here moves a device.** A migration is a copy: once credentials are
  provisioned, a device connects to the target and its twin in the source goes
  quiet. When to decommission the original stays a human decision.

## To confirm on a live tenant before building

Each of these is an assumption this concept rests on, and none of them has been
seen working. They are here rather than in the prose above on purpose. The column
on the right names the procedure in
[credentials-verification.md](credentials-verification.md).

**Option A's are all settled** — see the table above. What remains belongs to
Options C and B.

One residual risk rather than an assumption, recorded because it would be easy to
mistake for a platform fault: whether the registration file's **quoted commas** are
honoured. A device named `Pump, north` is entirely ordinary, and the writer quotes
it per RFC 4180, but nothing has confirmed the endpoint parses quoting. If it does
not, the device registers with its fields shifted rather than the file being
rejected. One row with a comma in `NAME` settles it.

| Assumption | Why it matters | Test |
| --- | --- | --- |
| Whether a trusted certificate can exist disabled in the target while still enabled in the source. | It is the difference between a cutover measured in seconds and one measured in minutes. | [C2](credentials-verification.md#c2--can-the-same-certificate-exist-in-both-tenants) |
| That certificate auto-registration binds a connecting device to the existing migrated object via its external identity. | If it creates a fresh object instead, the fleet arrives in the target detached from everything the migration carried over. | [C3](credentials-verification.md#c3--does-auto-registration-bind-to-the-migrated-object) |
| That a CA registered in the target works without proof of possession of its private key. | If proof is demanded, the copyable material stops being a public certificate and the option needs a key nobody in this chain holds. | [C4](credentials-verification.md#c4--does-the-target-demand-proof-of-possession) |
| Which permissions reading and writing trusted certificates needs. | Probably tenant-administrator level, which is a far larger ask of a subscribed tenant than the roles the manifest holds today — possibly large enough to make Option C operator-assisted rather than automatic. | [C6](credentials-verification.md#c6--what-permissions-do-trusted-certificates-need) |
| Whether a device can be attributed to the CA that signed its certificate. | Without it, Option C's coverage warning cannot be computed and has to be stated in the vaguest possible terms. | [C7](credentials-verification.md#c7--can-a-device-be-attributed-to-its-ca) |
| That the platform's API gateway lets a **device user** authenticate to a microservice endpoint at all. | Option B is impossible as written if it does not, whatever we build. | [B1](credentials-verification.md#b1--can-a-device-user-call-a-microservice-at-all) |
| That "the device a caller owns" resolves to exactly one managed object. | Option B's whole authorization chain hangs off it, and a gateway owning its children is the obvious counter-example. | [B2](credentials-verification.md#b2--can-the-service-resolve-the-device-a-caller-owns) |

## What the library already gives us

Worth recording, because it decided how the options are shaped — all of it
verified against the vendored go-c8y v2 source:

- `client.Devices.Registration` covers new device requests, `CreateCredentials`,
  `CreateBulk` (multipart CSV to `/devicecontrol/bulkNewDeviceRequests`),
  `GeneratePassword`, and `model.BulkRegistrationRecord` with a CSV writer.
  go-c8y-cli's own `deviceregistration register-basic` is built on exactly this,
  which is what makes admin-chosen passwords a blessed path rather than a trick.
- `client.Users` creates and updates users with a password in the body, and
  `ByDeviceUser(id)` knows the `device_` convention.
- `model.BulkRegistrationRecord`'s writer emits a fixed column order (`ID`,
  `AUTH_TYPE`, `CREDENTIALS`, `NAME`, `TYPE`, `IDTYPE`, `ICCID`, `TENANT`, `PATH`,
  `com_cumulocity_model_Agent.active`), and `SetBasicAuth` also sets `isAgent`.
  **But it writes them tab-separated** (`csvWriter.Comma = '\t'`), and the endpoint
  rejects tabs and accepts commas ([settled](#settled)) — so this writer cannot be
  used as it stands, whatever else Option A borrows from the library.
- `client.TrustedCertificates` lists, creates, updates and deletes per tenant, and
  the model carries `certInPemFormat`, `autoRegistrationEnabled` and `status` — so
  a CA's public certificate **is** readable from the source and creatable in the
  target. It also carries `tenantCertificateAuthority`, which is how the tool can
  recognise the per-tenant CA it must refuse to move.
- The same service exposes a **proof-of-possession** flow — `CreateVerificationCode`,
  `Proof`, `ProofEndToEnd`, `Confirm`, and `proofOfPossessionValid` on the model —
  and `ProofEndToEnd` needs the CA's **private key** to sign the verification code.
  Its existence is the reason [C4](credentials-verification.md#c4--does-the-target-demand-proof-of-possession)
  is on the list: if the target insists on it, Option C cannot move a CA on the
  strength of its public certificate alone.
