# Migrating device credentials

> **Status: a concept, not a description of behaviour.** Everything else under
> `docs/` says what the tool does; this one says what it could do about
> requirement #3, and none of it is implemented. It is here to be argued with
> before anybody writes code.

A migration copies a device hierarchy — the managed objects, their relationships,
their external identities and, on request, their measurements, events and alarms —
into a second tenant on the same platform. The source is left untouched: it is a
copy, not a move. What does not come across is the devices' ability to
authenticate, which is why [the README](../../README.md) lists *"device credentials,
so migrated devices do not reconnect on their own"* among the things a migration
does not cover.

This is the concept for closing that gap.

## Why credentials cannot simply be migrated

| | |
| --- | --- |
| **Device user** (basic auth) | The password is generated by the platform at registration and is never retrievable afterwards. The username is tenant-scoped, and the user belongs to the source tenant's user store. |
| **X.509 certificate** | The device's certificate chains to a CA the tenant trusts. A trusted certificate's fingerprint can be enabled in only one tenant per platform instance, and the platform routes a certificate-authenticated connection to whichever tenant trusts its chain. |
| **Access token** | Issued against a tenant after authenticating with one of the above, so it inherits their problems rather than solving them. |

The requirement suggests two ways out — an endpoint through which devices migrate
themselves, and a bulk credential download. Both are below, along with a third
that costs the devices nothing at all.

### One piece of existing machinery makes all three possible

External identities are already migrated
([internal/export/export.go:174](../../internal/export/export.go#L174),
[internal/importer/importer.go:347](../../internal/importer/importer.go#L347)), so a
migrated device carries the same external id in both tenants. And every object a
migration creates is stamped with that run's marker fragment. Those two facts are
how any of the options finds *the copy of this device, made by this migration*,
without a new mapping to keep.

## Option A — bulk credential provisioning

When a migration has succeeded, the operator asks the service for credentials for
that run. The service enumerates what the run created in the target tenant,
generates a password for each device, and creates the device users in one bulk
registration — binding each new user to the migrated object through its external
identity ([unconfirmed](#to-confirm-on-a-live-tenant-before-building): that the
platform binds rather than creating a second object). It streams a credentials
file back **once**: external id, tenant, username, password.

Getting those credentials onto the devices is the operator's own channel: a
configuration push through the source tenant while the devices are still
connected to it, a field technician, or their existing device-management tooling.
The job record notes that provisioning happened — when, by whom, how many — and
never the secrets themselves.

**Security model.** The caller is an administrator of the tenant the service is
deployed on, holding `ROLE_DEVICE_MIGRATION_ADMIN`: somebody who can already copy
whole tenants. Device credentials for the target are strictly less power than
they hold already. The passwords exist in the response and nowhere else — not in
the job record, which is an ordinary managed object any tenant administrator can
read.

**Asking twice.** Refused, naming the devices that already have users, unless
rotation is asked for explicitly. Rotation resets the passwords, which invalidates
any file handed out earlier. So *"I lost the file"* has an answer, and an old file
stops working rather than lingering.

**Assessment.** The highest value for the effort, and the only option with no
assumption whatsoever about the devices. Its weakness is honest: it ends with a
file somebody has to distribute.

## Option B — self-migration, the device asks for its own credentials

A device calls one endpoint on the microservice, authenticated with the
credentials it already has for the source tenant. It sends **no parameters**. The
service works out the rest:

1. The caller's credentials are proven against the platform.
2. The device it *owns* in that tenant is found — a device user owns its managed
   object.
3. That object's external identities are looked up in the target tenant, and the
   copy found there must carry the marker of a succeeded migration.
4. A device user is created for that copy, and the new tenant, username and
   password are returned once. Issuance is recorded on the target device object,
   without the secret.

**What stops a device asking for someone else's credentials.** The endpoint takes
no input, so there is nothing to tamper with. The chain runs from the
authenticated caller to the object it owns, to that object's identities, to the
migrated copy. Impersonating another device would mean attaching that device's
external identity to an object the attacker owns, which the platform refuses —
the identity is already taken.

**What it costs.** It is the first deliberate exception to a rule the service
applies everywhere else: only users of the tenant it is deployed on may call it
([internal/service/auth.go:36](../../internal/service/auth.go#L36)). That exception
needs its own authorizer, its own tests, rate limiting and an audit trail. And it
needs something outside our control — firmware that can call an endpoint and
switch credentials. Realistic where the customer owns the agent; not realistic for
closed firmware.

**Assessment.** The most elegant answer for fleets that can use it, and the
largest security surface in the proposal. Worth building when a fleet that can
actually call it exists — not before.

## Option C — move the trust anchor, not the devices

For a certificate fleet the credential is the chain, and the platform sends a
connection to whichever tenant trusts it. So migrating credentials becomes
migrating a trust anchor: read the trusted CA certificates from the source tenant,
recreate them in the target with auto-registration enabled, and at cutover disable
them in the source. The devices reconnect, arrive in the target, and
auto-registration binds each of them to its migrated copy through the external
identity that came with it — again
[unconfirmed](#to-confirm-on-a-live-tenant-before-building), and the whole option
rests on it.

Device involvement: none. No new certificate, no new password, no firmware change.

> **The unit is the CA, not the hierarchy.** Every device chained to that CA moves
> at once. A partial migration therefore cannot cut over safely unless the CA
> belongs exclusively to the hierarchy that was migrated. The tool should count
> the devices in the source that the run did *not* cover, and say so before
> offering a cutover.

**The cutover window.** Because a fingerprint cannot be enabled in two tenants at
once, there is an ordering question with a real availability cost: can the
certificate be pre-staged in the target while disabled and then flipped — a window
of seconds — or must it be removed from the source first? That is platform
behaviour to confirm, not to assume; see the table at the end.

**Deliberately not in the first cut.** Fleets enrolled against Cumulocity's own
per-tenant certificate authority cannot have that CA moved at all; they need
re-enrollment, which is a separate mechanism and a later increment. Per-device
certificates issued by a customer's own CA are covered by moving that CA.

**Assessment.** By far the least work for the devices, and a small amount of code.
Nearly all the difficulty is in the cutover ordering and in being honest about the
CA's blast radius.

## Scope boundaries worth stating

- **Devices behind a gateway or agent** that holds credentials on their behalf:
  the gateway is the device, as far as this is concerned.
- **Sending new credentials as an operation through the source tenant** works and
  is tempting, but it writes plaintext credentials into the source tenant's
  operation log. It belongs in an operator's runbook if they accept that; it
  should not be something the tool does for them.
- **Nothing here moves a device.** A migration is a copy: once credentials are
  provisioned, a device connects to the target and its twin in the source goes
  quiet. When to decommission the original stays a human decision.

## Recommended sequence

| | | |
| --- | --- | --- |
| 1 | This concept, reviewed | The security model of B and the blast radius of C are decisions to make with open eyes, before code. |
| 2 | **Option A**, in the service and the CLI, with a download in the UI | Highest value per unit of effort, no assumptions about the devices, and it reuses the run marker and identity plumbing that already exist. |
| 3 | **Option C**, with the coverage warning | Small amount of code once the platform's ordering rules are confirmed; removes the device work entirely for certificate fleets. |
| 4 | **Option B** | Largest security surface; worth its tests when a fleet that can call it exists. |

## To confirm on a live tenant before building

Each of these is an assumption this concept rests on, and none of them has been
seen working. They are here rather than in the prose above on purpose.

| Assumption | Why it matters |
| --- | --- |
| A bulk-registration row whose external id already exists binds the new device user to the existing managed object rather than creating a second one. | Option A depends on it entirely. If it duplicates, the approach changes to creating users directly. |
| Which permissions the service user needs for bulk registration in the target tenant. | New permissions mean a manifest change that every subscribed tenant's administrator has to approve on upgrade. |
| Whether a trusted certificate can exist disabled in the target while still enabled in the source. | It is the difference between a cutover measured in seconds and one measured in minutes. |
| That certificate auto-registration binds a connecting device to the existing migrated object via its external identity. | If it creates a fresh object instead, the fleet arrives in the target detached from everything the migration carried over. |

## What the library already gives us

Worth recording, because it decided how the options are shaped — all of it
verified against the vendored go-c8y v2 source:

- `client.Devices.Registration` covers new device requests, `CreateCredentials`,
  `CreateBulk` (multipart CSV to `/devicecontrol/bulkNewDeviceRequests`),
  `GeneratePassword`, and `model.BulkRegistrationRecord` with a CSV writer.
  go-c8y-cli's own `deviceregistration register-basic` is built on exactly this,
  which is what makes admin-chosen passwords a blessed path rather than a trick.
- `client.Users` creates and updates users with a password in the body, and
  `ByDeviceUser(id)` knows the `device_` convention.
- `client.TrustedCertificates` lists, creates, updates and deletes per tenant, and
  the model carries `certInPemFormat`, `autoRegistrationEnabled` and `status` — so
  a CA's public certificate **is** readable from the source and creatable in the
  target.
