# Internals

Why the tooling is shaped the way it is, and how to work on it. Nothing here is
needed to *use* either implementation — start from [the main
README](../README.md) for that.

The companion document is
[go-port/BEHAVIOUR-CONTRACT.md](go-port/BEHAVIOUR-CONTRACT.md), which records
what the two implementations have to agree on, down to the trailing newline, and
which of the library's helpful defaults had to be undone to get there.

## Why there are two implementations

The extension in `commands/` is bash, and it reaches Cumulocity by shelling out
to `c8y` for every single operation. That subprocess boundary caused nearly every
bug this tool has had:

- `c8y` draining the stdin pipe that was driving a `while read` loop, so only the
  first child of each parent was assigned
- ambient `C8Y_*` variables quietly winning over `--session`
- `sessions get` ignoring `--session` altogether
- records failing to lex when inlined as jsonnet
- `jq`'s `@tsv` doubling backslashes and corrupting records in transit

None of those are logic errors. They are all consequences of talking to a CLI
instead of an API. The [standalone binary](cli.md) uses the **go-c8y v2** library
instead: a typed client with two explicit tenants removes that whole class by
construction — no subprocess, no ambient environment, no shell quoting, no pipes.

The extension remains the supported one. The binary exists so that it can
eventually replace it, and until then the two are held to the same behaviour.

## Why sessions are read from disk

The identity comes from reading the session files, not from asking c8y.
`c8y sessions get --session X` **does not report session X** — it reports
whichever session is active and ignores `--session`, so with a source session
loaded it answers "source" for both sides and the same-tenant check refuses a
good migration. `host` and `tenant` are plaintext in a session file even when
`password` and `token` are encrypted, so reading them needs no passphrase, no
network and no active session.

For the same reason every call clears the ambient `C8Y_*` variables and sets
`C8Y_SESSION` explicitly. Activating a session exports `C8Y_HOST` and
`C8Y_TENANT`, and those otherwise decide which tenant is talked to whatever
`--session` says. `C8Y_PASSPHRASE` is deliberately kept — without it an
encrypted session file cannot be decrypted at all.

The file each argument resolved to is what the export and import are given, so
the tenants named above are the tenants used. A glob is never resolved twice.

## One fragment per object

**One fragment per object, deliberately.** There is no second, constant
`c8y_DeviceMigration` fragment, so "what did this tool ever create in this
tenant?" is not an indexed query — `fragmentType` matches a fragment name
exactly, and the inventory query language wildcards fragment *values*, not
names. Answering it means either knowing the run ids, which the mapping files
and journals record, or a client-side `--filter` over the whole inventory. That
was weighed against stamping a second fragment onto every migrated object, and
the single run-scoped marker won.

## How the two are kept in step

`make go-test` includes a **differential test**: it runs `commands/export` against
the fake `c8y` and the Go export against an HTTP server, both driven from
`tests/fixtures/hierarchy.json`, and then asserts the two output directories are
identical file-for-file and byte-for-byte and that stderr matches line-for-line.
The object bodies the Go server returns are generated by invoking the fake
itself, so the two really do receive the same bytes and any difference is a
difference in behaviour rather than in the harness.

`import` is compared the same way, but its interesting output is what reached
the tenant rather than files on disk: `id_mapping.json` byte for byte, stderr
line for line, and the created objects, external identities and relationships
matched by **source** id. Request bodies are compared as parsed JSON, because the
bash side builds them with jq and the Go side edits the raw document with sjson —
whitespace in a request body is not behaviour.

`import` also refuses to import back into the tenant the export came from, which
`migrate` guards but the separate commands never did. It looks up an exported
object by its **source** id: ids are tenant-scoped, so an id that resolves to an
object with the same name, type and creation time is the same object, and so the
same tenant. It does not compare hostnames, because `self` carries whatever host
the platform chose and a mismatch says nothing. `--allowSameTenant` overrides it.

One thing the differential test cannot see, and a separate test therefore asserts
directly:
managed object bodies are written to disk **verbatim**. Go's `encoding/json`
renders `float64(600)` as `600` and cannot distinguish an absent field from an
explicit `null`, and `tests/fixtures/export-9object/` — captured from a real
tenant — contains both. Re-encoding a body would silently rewrite a customer's
data. The fake happens to pretty-print with the same two-space indent Go would
use, so the differential test is blind to it; the byte-for-byte test is not.

The 254 bats tests still guard the bash implementation only. Most of them assert
against the fake's record of `c8y` invocations — `--nullInput`, `--batchSize 50`,
which session each call used — and a library-based tool makes no such calls, so
those assertions are meaningless for it and are deliberately not faked into
passing.

## Releasing

Two things are released, and the extension is not one of them: it is installed
straight from the repository by `c8y extension install`, so there is no artefact
to build for it.

| | |
| --- | --- |
| the command line tool | `c8y-devicemigration-<version>-<os>-<arch>.tar.gz`, and `.zip` for Windows, for darwin and linux on arm64 and amd64 plus 64-bit Windows. Each holds the binary, `LICENSE`, `README.md` and `docs/`, and `SHA256SUMS` covers them all |
| the microservice | `devicemigration-<version>.zip`, the manifest and image the platform is fed, and the same image in the registry at `ghcr.io/<owner>/c8y-devicemigration/microservice` |

Both carry the same version, and both binaries report it — `c8y-devicemigration
--version`, and the microservice logs it at startup. It is stamped at link time
from `internal/version`.

### Versions

[VERSION](../VERSION) holds the version being developed — the one the next
release will carry — and it is the only place a version is written down. What a
build calls itself is derived from that file and from git:

| the build | what it says |
| --- | --- |
| an exact `v` tag on a clean tree | `0.2.0` — a release |
| anything else | `0.2.0-SNAPSHOT` |

```sh
make version                    # what this build would call itself
make dist                       # the archives, into dist/
make service-package            # the microservice zip, into build/
make dist VERSION=1.2.0         # what a release of 1.2.0 would contain
```

**Snapshots are the default.** The old default took the *nearest* tag, so a
working tree with a fortnight of unreleased work in it built an image labelled
exactly like the released version — and once that is deployed, nothing about the
running service says whether it is current. That cost an afternoon of looking for
a bug in code the platform was not running. `0.2.0-SNAPSHOT` cannot be mistaken
for `0.2.0`.

**One snapshot version rather than one per commit**, so every upload replaces the
same version instead of leaving a list behind. The cost is that two snapshot
builds cannot be told apart by their version; when that question comes up, the
answers are to release, or to pass `VERSION` explicitly.

`make check` runs `version-check`, which refuses a `VERSION` file that is not a
plain `X.Y.Z` — the suffix is the build's to add — and, on a release build,
refuses a tag that disagrees with the file.

### Tags, and releasing

Tags still decide what a release is; `VERSION` decides what it is allowed to be
called. Four steps:

```sh
$EDITOR VERSION                      # 1. the version being released
git commit -am "release 1.2.0"       # 2. it has to be in a commit to be tagged
make tag                             # 3. creates v1.2.0 on that commit
git push origin v1.2.0               # 4. builds and publishes it
```

`make tag` refuses a dirty tree — a tag names a commit, and uncommitted work is
not in one — refuses a version that is already tagged, and refuses anything
`version-check` would refuse. It does not push: that is the irreversible half,
and it was never the part that needed automating. Tagging by hand
(`git tag v1.2.0`) works exactly as before; the target is a shortcut, not a
gate.

Afterwards, bump `VERSION` again so builds go back to calling themselves
snapshots of something newer.

The tag and the file must agree on their `X.Y.Z` core. A tag that disagrees is
refused by the release workflow in its first job, before anything is built —
publishing a version this repository never said it was working towards is worse
than a failed release. A pre-release of a declared version is fine: `v0.3.0-rc1`
while the file says `0.3.0`.

That runs [.github/workflows/release.yml](../.github/workflows/release.yml),
which resolves the version once, refuses it unless it is SemVer — the platform
rejects a manifest that is not — runs the Go checks and the whole bats suite
before building anything, then produces the archives, the microservice zip and a
multi-architecture image, and opens a **draft** release with all of it attached.
The draft is deliberate: the notes are generated and somebody should read them
before this is what people download. Publish with
`gh release edit v1.2.0 --draft=false`.

A tag with a pre-release identifier (`v1.2.0-rc.1`) is marked as a pre-release
and does not move the image's `latest` tag.

To find out whether a release would work without making one, run the workflow
manually from the Actions tab with a version: everything is built and nothing is
published.

## Development

The test suite runs entirely against a fake `c8y` on `PATH`, so it never touches
a tenant and needs no session.

```sh
make check              # everything below: bash and Go
make go-build           # build bin/c8y-devicemigration
make go-test            # Go tests, including the bash-vs-Go differential test
make go-lint            # gofmt and go vet
make install            # -> $(INSTALL_DIR), default ~/.local/bin
make install-completion  # the binary plus the zsh completion script
make test       # tests only (bootstraps bats into tests/vendor on first run)
make test-fast  # the same tests across every core, needs GNU parallel
make lint       # shellcheck, skipped with a warning if not installed
make docs       # regenerate the command reference in docs/extension.md
```

The **Commands** section of [extension.md](extension.md) is generated from the
`DOC` string of each command by `tools/gen-command-docs.sh`, between the
`<!-- BEGIN COMMAND REFERENCE -->` markers. Run `make docs` after changing an
option; `make check` and CI fail if it was not. Hand-editing an option list
there is exactly the drift nobody notices until someone follows the docs and it
does not work.

`make test` is sequential, which is what you want when debugging one failure.
`make test-fast` is the same suite with `bats --jobs`, and takes about a quarter
of the time; CI uses it. `make test JOBS=4` picks a specific level.

Two things keep the suite quick enough to run casually. Tests are parallel-safe
because every piece of per-test state lives under `$BATS_TEST_TMPDIR` — keep it
that way, and in particular do not assert against the shared temp directory,
since concurrent tests write there too. And identical exports and imports are
memoised per file by `shared_export` and `shared_migration` in
`tests/helpers/load.bash`: the first test needing a given invocation runs it and
the rest get a private copy.

The cache key covers the arguments **and** the `FAKE_C8Y_*` environment. Both
halves matter: per-test paths are normalised out of it or it would never hit,
and the environment is included because two runs with the same arguments but a
different hierarchy fixture are not the same run. A test that mutates what it is
given should call `run_export`/`run_import` directly rather than the memoised
helpers.

The fake can be made to fail on purpose, which is how the interruption paths are
tested: `FAKE_C8Y_FAIL_CREATE_NAME` stops an import at one named object, and
`FAKE_C8Y_FAIL_DATA_AFTER` lets a number of data creates through and then
refuses, so the failure lands *inside* a device's data rather than neatly
between two devices. The full list is at the top of `tests/fake/c8y`.

`tests/fixtures/hierarchy.json` describes the fake tenant. It is shaped
deliberately: three parents have two children of the same type, because a parent
with a single child cannot expose the class of bug where `c8y` consumes the
stdin pipe driving a `while read` loop and only the first child is processed.
It also contains a cycle, an object with two parents, an addition-only branch,
an unnamed object, and names carrying quotes, brackets, tabs and non-ASCII.

Every command parses its arguments with a generated docopt parser held between
the `# docopt parser below/above` markers. After editing a `DOC` string, regenerate
it or every invocation will exit 70:

```sh
docopt.sh commands/export      # pipx install docopt-sh==2.0.3
```

### What the tests cannot cover

The fake encodes assumptions about real `c8y` behaviour, listed at the top of
`tests/fake/c8y`. All of them have been confirmed against a live tenant, and
every command path has been exercised there at least once: export, import
including external identities, and revert. Any change to those assumptions
should be recorded in that file, since a fake that quietly drifts is worse than
no test at all.

The jsonnet templates that strip server managed properties are evaluated for
real in the suite, using `c8y template execute`, which needs no session and no
network. Those tests assert the resulting body rather than the template text,
and they skip when `c8y` is not installed so the suite stays hermetic in CI.

The suite still cannot see a real tenant, so after changing anything that talks
to `c8y`, smoke it manually:

1. `c8y devicemigration export --rootId <id> --output-directory ./smoke`
2. Check one `exported_device_*.json` looks like the managed object, and that
   each `*_child_*.json` is a JSON array holding every child.
3. Switch to a throwaway tenant and import with `--force`.
4. Confirm the reported link count matches the number of references in the
   export, and spot-check the hierarchy in the UI.
5. Check the `Added external identity ...` lines appear for any device that had
   external IDs, and that those IDs resolve in the target tenant.
